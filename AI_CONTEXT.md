# 🤖 Work-Analytics: Контекст проекта для разработчиков и ИИ-агентов

Этот документ представляет собой подробное техническое руководство, карту архитектуры и базу знаний проекта **Work-Analytics**. Он разработан специально для того, чтобы разработчики и ИИ-агенты могли мгновенно войти в контекст системы, понять её внутреннее устройство, структуры данных, алгоритмы и особенности интеграций, а также легко подготовиться к защите проекта.

---

## 📖 1. Описание проекта

**Work-Analytics** — это интеллектуальный агрегатор ИТ-вакансий с интегрированным AI-анализом. Система собирает вакансии с популярных платформ, дедуплицирует их, нормализует зарплатные предложения к единой валюте (RUB) и обогащает сырые данные с помощью больших языковых моделей (LLM) через API Groq.

### Ключевой функционал:
- 🕵️‍♂️ **Параллельный парсинг** вакансий с официальных API (hh.ru, rabota.by) и HTML-скрейпинга (Habr Career).
- 🧠 **Многопоточное AI-обогащение** (извлечение Hard/Soft навыков, грейда, вилки стажа, требуемого опыта, формата работы, владения английским языком, категории специальности и требований к образованию).
- 💱 **Нормализация валют** (автоматический сбор курсов через ExchangeRate-API и приведение всех зарплат к рублям).
- 🔄 **Продвинутый движок дедупликации (Entity Resolution)** на основе схожести Жаккара, транслитерации и интеллектуального слияния полей.
- ⏳ **Менеджер фоновых задач (FIFO)** с поддержкой отмены через `AbortController` и трансляции прогресса на клиент в реальном времени через SSE (Server-Sent Events).
- 🎨 **Премиум-интерфейс**: адаптивное SPA на чистом JS с поддержкой динамических тем (Glassmorphic), кастомных настроек и авто-перерисовки графиков (Chart.js).

## ⚙️ 3. Ключевые сервисы и логика их работы

### 🧠 3.1. AI-сервис (`server/services/ai.js`)
Этот сервис выполняет структурированный анализ сырых текстов вакансий через **Groq API** (совместимый с OpenAI протокол).
- **Многопоточный пул воркеров (Parallel Multi-Key Worker Pool)**: 
  Если в `.env` настроено несколько ключей API в переменной `GROQ_API_KEYS` (через запятую), сервис запускает параллельные независимые воркеры (по одному на каждый ключ). Это кратно увеличивает RPS (запросов в секунду) и общую скорость сбора данных.
- **Динамический размер батча (Dynamic Batching)**:
  - Обычный сбор вакансий: батчи по **10 вакансий**.
  - Глубокий сбор (`isDeepScrape = true`): батчи по **5 вакансий** (для уменьшения размера контекста и повышения точности LLM).
- **Отказоустойчивость и ротация моделей (Model Fallback)**:
  При получении ошибки лимитов (HTTP 429) или квот (401, 402, 403), поток автоматически переключается на следующую модель из списка `GROQ_MODELS` и делает паузу с экспоненциальной задержкой. У каждого потока свой изолированный индекс текущей модели.
- **Ограничение частоты запросов (Rate Limiting)**:
  Для каждого API-ключа строится цепочка обещаний (Promise Chain), гарантирующая паузу `BATCH_DELAY_MS` (2100мс) между последовательными обращениями, что защищает от блокировок.

### 🔄 3.2. Дедупликация (`server/services/dedup.js`)
Использует кастомный алгоритм текстовой схожести и транслитерации для очистки и слияния вакансий.
- **Транслитерация**: перевод кириллических заголовков в латиницу для сопоставления смешанных терминов (например, "разработчик" -> "razrabotchik").
- **Очистка от стоп-слов**: из названий вакансий вырезаются грейды ("junior", "middle", "senior", "lead") и роли ("developer", "engineer", "razrabotchik"), чтобы получить чистое ядро технологий.
- **Сходство Жаккара (Jaccard Similarity)**: токенизированные массивы сравниваются по формуле $|A \cap B| / |A \cup B|$.
- **Слияние дубликатов (`mergeJobs`)**: при совпадении вакансий они объединяются: дополняется вилка зарплаты, объединяются массивы навыков (уникальный набор), выбирается более длинное описание, а исходные ссылки сохраняются в массив `mergedFrom`.

### ⏳ 3.3. Менеджер очереди задач (`server/services/queue.js`)
Позволяет пользователю запускать длительный парсинг в фоне.
- Очередь вмещает до 50 задач. Одновременно выполняется **ровно одна задача** (`isProcessing = true`).
- Предусмотрена возможность досрочной отмены задачи (`gracefulStop` / `deleteTask`). При отмене срабатывает `AbortController`, прерывающий активные HTTP-запросы в парсерах и ИИ-генераторе.
- Лимит на выполнение одной задачи — **15 минут**, после чего задача прерывается по таймауту для разблокировки очереди.
- Изменения статуса транслируются клиенту в реальном времени через Express SSE (роут `/api/events`).

### 💾 3.4. База данных (`server/services/storage.js`)
Хранилище основано на двух файлах:
- **`data/reports/index.jsonl` (JSON Lines)**: быстрый транзакционный журнал (Event Sourcing). Содержит только метаданные отчетов (поисковый запрос, дата создания, статистика, ошибки). Используется для моментального отображения списка отчетов на дашборде. При удалении записи в конец файла просто дописывается строка с флагом `_deleted: true`. Периодически выполняется авто-компактизация файла.
- **`data/reports/report_*.json`**: файлы, хранящие полные данные отчетов, включая массив всех вакансий со всеми метаданными. Загружаются только при детальном просмотре отчета.
- **Безопасность**: Пути валидируются регулярным выражением и принудительно проверяются на Path Traversal атаки через `path.resolve` и префикс-проверку директории.

Сервер предоставляет следующие HTTP-эндпоинты (префикс `/api`):

| Метод | Путь | Описание | Параметры / Тело запроса |
| :--- | :--- | :--- | :--- |

| **GET** | `/api/queue` | Получить текущее состояние очереди и активную задачу | Нет |
| **POST** | `/api/queue/:id/delete`| Удалить задачу из очереди | `:id` |
| **POST** | `/api/queue/:id/stop` | Мягко остановить выполнение активной задачи | `:id` |
| **POST** | `/api/queue/:id/priority`| Переместить задачу в начало очереди (приоритет) | `:id` |

## 💡 7. Подробная база знаний по ключевым механизмам (для защиты проекта)

Этот раздел содержит подробное словесное описание алгоритмов и архитектурных решений проекта. Информация структурирована так, чтобы вы могли уверенно ответить на любой технический вопрос научного руководителя без необходимости заучивать синтаксис кода.

### 7.1. Умная очередь фоновых задач (FIFO) и SSE-вещание
**Как это работает:**
1. Когда пользователь запускает парсинг, сервер не начинает его мгновенно в контексте HTTP-запроса (так как парсинг и AI-анализ могут занимать минуты, что привело бы к HTTP-таймауту). Вместо этого запрос возвращает статус `202 Accepted` и уникальный `taskId`, а задача помещается в массив-очередь `taskQueue` (максимум 50 задач).
2. Сервер обрабатывает задачи **строго последовательно (FIFO — First In, First Out)**. За это отвечает переменная `isProcessing`. Если она равна `false`, сервер извлекает первую задачу со статусом `pending`, устанавливает `isProcessing = true` и запускает конвейер.
3. **Зачем это нужно:** Ограничение параллельного сбора одной задачей критически важно для защиты от банов (Rate Limit). Если бы 10 пользователей одновременно запустили парсинг hh.ru и Habr Career с одного IP-адреса сервера, внешние платформы мгновенно заблокировали бы IP-адрес за подозрительную активность.
4. **SSE-вещание:** Клиентское приложение подключается к эндпоинту `/api/events` через стандартный браузерный механизм `EventSource`. Это постоянное однонаправленное текстовое соединение. Сервер, используя `EventEmitter`, при любом изменении шага сбора или прогресса задачи генерирует событие `taskUpdate` и отправляет его в открытые сокеты-соединения. Это позволяет фронтенду отрисовывать прогресс-бар и лог шагов в реальном времени без постоянных тяжелых AJAX-запросов (polling).

### 7.2. Устойчивость к отказам парсинга (Retry с экспоненциальным бэкоффом)
**Как это работает:**
1. Сетевые запросы к внешним сайтам нестабильны: сервер Habr Career может вернуть ошибку 503 из-за нагрузки, или API HH временно оборвет соединение. В `pipeline.js` внедрен механизм автоматических повторных попыток (**Retry**).
2. Для каждого выбранного источника запускается цикл из **3 попыток**. Если запрос завершается ошибкой, скрипт перехватывает её, анализирует (не вызвана ли она отменой пользователем) и рассчитывает время ожидания перед следующим повтором по формуле экспоненциальной задержки: `attempt * 3000ms` (3 сек после первой неудачи, 6 сек после второй).
3. **Отказоустойчивость (Partial Status):** Если источник окончательно «умер» после 3 попыток, весь пайплайн не падает с ошибкой. Скрипт записывает имя сбойного источника в массив `errors`, продолжает работу с оставшимися платформами, а в конце сохраняет отчет со статусом `partial` (частичный). Это гарантирует, что пользователь получит хоть какие-то данные, даже если одна из платформ временно недоступна.

### 7.3. Двухканальное управление и отмена сбора (AbortController)
**Как это работает:**
1. Если пользователь видит, что сбор затянулся, или он ввел не тот запрос, он может нажать кнопку «Остановить». На сервер отправляется POST-запрос на эндпоинт `/api/queue/:id/stop` или `/api/queue/:id/delete`.
2. Сервер находит задачу в очереди и меняет флаг `task.cancelFlag.isStopped = true`. Одновременно вызывается метод `.abort()` у встроенного в JavaScript объекта `AbortController`, который был создан специально для этой задачи при старте.
3. Сигнал отмены (`abortController.signal`) прокинут во все внутренние асинхронные операции:
   - В сетевые запросы `axios` (что мгновенно обрывает активные HTTP-запросы к HH, Habr и Groq на уровне сетевого сокета Node.js).
   - В циклы ожидания (бэкоффы и задержки AI воркеров), которые мгновенно выбрасывают исключение отмены и завершаются.
   - В циклы конкурентного парсинга вакансий в `BaseParser`, где на каждой итерации проверяется `cancelFlag.isStopped`.
4. **Результат:** Ресурсы сервера освобождаются мгновенно. Если к моменту отмены часть данных уже была успешно собрана, пайплайн мягко останавливается, сохраняя промежуточный отчет со статусом `partial` (если включен graceful stop), и запускает следующую задачу из очереди.

### 7.4. Многопоточное AI-обогащение с пулом ключей (Parallel Worker Pool)
**Как это работает:**
1. AI-анализ — самая медленная часть системы. Для анализа 100 вакансий требуется сделать множество запросов к LLM. Для решения этой проблемы реализован **многопоточный воркер-пул**.
2. Сервер считывает список API-ключей из переменной `GROQ_API_KEYS` (разделитель — запятая). На каждый валидный ключ создается независимый виртуальный поток-воркер (асинхронная функция `worker`). Все воркеры одновременно разбирают общую очередь батчей вакансий.
3. **Динамический батчинг:** Вакансии бьются на группы (батчи). При обычном сборе размер батча — 10 вакансий, при глубоком — 5 вакансий (глубокий сбор анализирует полный текст вакансии, поэтому батч уменьшается во избежание переполнения лимита токенов LLM).
4. **Контроль частоты (Rate Limit Chain):** У моделей Groq жесткие лимиты на количество запросов в минуту (RPM). Чтобы ключи не блокировались, для каждого ключа в `Map` хранится цепочка промисов. Перед отправкой запроса воркер вызывает `waitForRateLimit(apiKey)`, который выстраивает запросы строго в очередь с обязательной паузой в `2100мс` друг за другом для конкретного ключа.
5. **Ротация моделей (Fallback):** Если ключ все же ловит ошибку квоты или лимита (HTTP 429), воркер не падает. Он ловит ошибку, сдвигает локальный индекс моделей на следующую доступную в `.env` (например, переключается с быстрой `llama-3.1-8b-instant` на мощную `llama3-70b-8192`), увеличивает паузу ожидания и пробует отправить этот же батч снова.

### 7.5. Алгоритм дедупликации (Entity Resolution)
**Как это работает:**
1. Вакансии на разных сайтах часто дублируются (работодатель выложил одну вакансию и на HH, и на Хабр). Алгоритм дедупликации в `dedup.js` сопоставляет их в несколько этапов:
2. **Этап 1. Транслитерация и нормализация:** Все названия переводятся в нижний регистр, очищаются от спецсимволов. Буквы кириллицы заменяются латинскими аналогами по таблице транслитерации. Это решает проблему разного написания (например, "Системный администратор" и "Sistemny administrator" станут идентичными строками).
3. **Этап 2. Вырезание неинформативного шума:** Из названий удаляются грейды (Junior, Middle, Senior, Lead, Главный, Ведущий...) и роли (Developer, Engineer, Программист, Разработчик...). Если мы ищем "Senior React Developer", то после очистки останется просто "react". Это позволяет сравнивать вакансии по их технологической сути.
4. **Этап 3. Сходство Жаккара (Jaccard Similarity):** Сравниваются множества слов в названиях вакансий по формуле: отношение количества общих слов к общему количеству уникальных слов в обоих названиях.
   - Если компании совпадают на 70%, а очищенные заголовки вакансий похожи более чем на 70% (порог `JACCARD_THRESHOLD_TITLE = 0.7`) -> вакансии признаются дубликатами.
   - Если сходство названий супер-высокое (более 85%), но компании написаны чуть по-разному (например, "Яндекс" и "ООО Яндекс.Технологии"), то алгоритм сравнивает названия компаний по Жаккару с порогом 70%. Если сходство пройдено -> это дубликаты.
5. **Этап 4. Блокировка (Blocking Key Optimization):** Сравнение каждой вакансии с каждой при больших объемах работает очень медленно ($O(N^2)$ операций). Для оптимизации применен метод блокировки: для каждой вакансии генерируется блокирующий ключ из первых двух очищенных токенов названия. Сравниваются между собой только вакансии внутри одного блока (с одинаковым ключом). Это снижает сложность алгоритма до близкой к линейной ($O(N)$).
6. **Этап 5. Умное слияние (`mergeJobs`):** Дубликат не просто удаляется. Данные объединяются:
   - Если у одной вакансии указан только минимум зарплаты, а у другой только максимум — формируется полная вилка.
   - Массивы навыков (skills) объединяются в один уникальный массив (без повторений).
   - Берется наиболее длинное и подробное описание вакансии.
   - Ссылка на удаленный дубликат сохраняется в историю слияния `mergedFrom` основной вакансии.

### 7.6. Высокопроизводительное файловое хранилище (Event Sourcing)
**Как это работает:**
1. Традиционный подход — хранить все данные в одном большом JSON-файле и перезаписывать его при любом изменении. Это привело бы к колоссальным тормозам диска и риску порчи всей базы данных при сбое питания.
2. В проекте реализован паттерн **Event Sourcing** на плоских файлах в директории `data/reports/`:
   - Каждый детальный отчет со всеми вакансиями (тяжелый файл) хранится отдельно: `report_*.json`. Он считывается с диска только тогда, когда пользователь непосредственно открывает этот отчет в интерфейсе ("ленивая загрузка").
   - Список всех отчетов для вывода в боковую панель хранится в сверхбыстром файле `index.jsonl` (JSON Lines). Каждая строка в нем — это независимый JSON-объект с метаданными (без массива вакансий).
3. **Добавление отчета:** Сервер не переписывает индексный файл целиком. Он просто открывает его и дописывает в самый конец одну новую строчку (операция **appendFile**). Это моментальная операция, не зависящая от размера базы данных.
4. **Удаление отчета:** При удалении сервер не пересобирает файл. Он просто дописывает в конец лога строчку `{ "id": "report_id", "_deleted": true }`.
5. **Кэширование и компактизация:** При запуске сервера `storage.js` считывает `index.jsonl` построчно. Он наполняет `Map` в оперативной памяти: обычные записи добавляет, а при встрече строки с флагом `_deleted` — удаляет из памяти. После этого в фоне запускается компактизация: кэш из памяти записывается в новый чистый `index.jsonl.tmp` без удаленных записей, который затем атомарно переименовывается в `index.jsonl`. Это гарантирует моментальный отклик интерфейса и сохранность данных.

### 7.7. Нормализация валют и расчет средних зарплат
**Как это работает:**
1. Вакансии публикуются в разных валютах: RUB, BYN, USD, EUR, KZT. Сравнивать их напрямую невозможно.
2. При старте пайплайна сервер вызывает `fetchExchangeRates()`. Этот метод обращается к ExchangeRate-API, запрашивает актуальные курсы и сохраняет снимок этих курсов (с отметкой даты) прямо внутрь создаваемого отчета.
3. Все зарплатные предложения нормализуются. Если указана вилка `min` и `max`, рассчитывается среднее арифметическое значение вакансии в ее оригинальной валюте. Если указан только один из параметров — берется он.
4. Полученное значение конвертируется в рубли (RUB) по курсу из снимка отчета.
5. На основе всех сконвертированных зарплат рассчитывается средняя нормализованная зарплата по всему отчету (`stats.avgSalaryNormalized`), которая выводится в главном виджете дашборда.
6. **Зачем сохранять снимок курсов в отчете:** Курсы валют постоянно меняются. Если бы мы пересчитывали зарплаты по текущему курсу каждый раз при открытии старого отчета, графики и цифры «плыли» бы каждый день. Сохранение курсов на момент создания отчета гарантирует историческую точность и воспроизводимость аналитики.

### 7.8. Единое перехватываемое логирование
**Как это работает:**
1. Для отладки и контроля работы сервера критически важно видеть подробный лог. Но стандартный вывод в консоль терминала теряется при перезапуске сервера.
2. В `server/app.js` переопределены стандартные методы глобального объекта: `console.log`, `console.warn` и `console.error`.
3. При их вызове сервер:
   - Выводит цветное стилизованное сообщение в стандартный вывод терминала разработчика (для удобства чтения глаз).
   - Одновременно форматирует сообщение (добавляет точную дату, время и уровень лога `[INFO]`, `[WARN]`, `[ERROR]`), полностью вырезает из строки ANSI-коды окрашивания (чтобы файл не засорялся нечитаемыми символами) и дописывает (append) строчку в файл `data/server.log`.
4. В результате разработчик всегда может открыть `data/server.log` и увидеть хронологию работы сервера, включая детальные ошибки парсеров и AI-батчей за любой период времени.
