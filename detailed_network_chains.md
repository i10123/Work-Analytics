# Подробное пошаговое описание сетевых взаимодействий в проекте "Work-Analytics"

В этом документе каждое сетевое взаимодействие в системе разобрано на уровне микро-шагов. Описание составлено без непосредственного программного кода, но максимально близко к логике его выполнения, чтобы вы могли детально представить и объяснить комиссии работу каждого сетевого узла.

---

## Взаимодействие 1: Запуск парсинга и ограничение частоты запросов
**Маршрут**: `POST /api/parse`  
**Тип**: Клиент-Серверный REST-запрос (HTTP/1.1)

```
[Браузер] --(1. HTTP POST с JSON-параметрами)--> [Промежуточное ПО: Rate Limiter]
                                                           |
                                      (Проверка: превышен ли лимит запросов?)
                                         /                           \
                                     (Да)                            (Нет)
                                     /                                 \
           [HTTP 429: Предупреждение]             [Express Маршрутизатор]
                                                                         |
                                                   [Сервис Очереди: In-Memory Queue]
                                                                         |
                                               [HTTP 202: Подтверждение о принятии]
```

### Цепочка микро-шагов:
1.  **Действие пользователя**: Пользователь вводит поисковой запрос (например, "React developer"), выбирает источники (HH, Habr), указывает период, стоп-слова и нажимает кнопку "Начать сбор" в интерфейсе.
2.  **Формирование запроса на клиенте**: Фронтенд-скрипт собирает эти параметры в единый JavaScript-объект и делает асинхронный вызов `fetch('/api/parse', ...)`.
    *   **Метод**: `POST`.
    *   **Заголовки (Headers)**: `Content-Type: application/json`.
    *   **Тело запроса (Body)**: JSON-строка, содержащая: `query`, `period`, `limit`, `sources`, `stopWords`, `deepScrape` и `clientId` (уникальный идентификатор вкладки браузера).
3.  **Передача по сети**: Запрос передается по протоколу TCP/IP на порт сервера (по умолчанию `3000`).
4.  **Слой Rate Limiter на сервере**: Первым запрос принимает промежуточный обработчик `express-rate-limit`. Он считывает IP-адрес отправителя и проверяет внутренний счетчик в оперативной памяти сервера.
    *   *Сценарий А (Лимит превышен)*: Если с этого IP было отправлено более 15 запросов за последние 15 минут, сервер сразу же прекращает обработку, закрывает сетевое соединение и отправляет клиенту статус `HTTP 429 Too Many Requests` с JSON-сообщением об ошибке.
    *   *Сценарий Б (Всё в порядке)*: Запрос пропускается дальше.
5.  **Слой парсинга JSON на сервере**: Встроенный парсер Express (`express.json`) считывает тело запроса. Он проверяет размер данных (лимит — 100 килобайт для предотвращения переполнения памяти) и преобразует сырую текстовую строку JSON в стандартный объект Node.js.
6.  **Маршрутизация**: Запрос попадает в обработчик пути `/api/parse` внутри файла `routes/api.js`.
7.  **Валидация данных**: Сервер проверяет переданные параметры:
    *   Строка запроса `query` не должна быть пустой и не должна превышать 200 символов.
    *   Лимит вакансий принудительно ограничивается диапазоном от 5 до 200 штук.
    *   Если валидация не пройдена, сервер возвращает статус `HTTP 400 Bad Request` с описанием ошибки.
8.  **Добавление в очередь задач**: Если данные верны, вызывается функция `enqueueTask` из сервиса `queue.js`.
    *   Генерируется уникальный идентификатор задачи на основе транслитерации поискового слова и текущего времени (например, `report_React_developer_2026-05-28_18-30-00`).
    *   В массив очереди `taskQueue` добавляется объект задачи со статусом `"pending"`.
9.  **Сетевой ответ клиенту**: Сервер отправляет клиенту быстрый ответ:
    *   **Статус**: `HTTP 202 Accepted` (запрос принят в обработку, но сам парсинг еще не начался).
    *   **Тело ответа**: JSON со статусом успеха (`success: true`) и сгенерированным ID задачи. Сетевое соединение для этого HTTP-запроса закрывается.

## Взаимодействие 2: Подключение и вещание в реальном времени (SSE)
**Маршрут**: `GET /api/events`  
**Тип**: Серверная отправка событий (Server-Sent Events) по постоянному HTTP-соединению

```
[Браузер (EventSource)] --(1. HTTP GET /api/events?clientId=...)--> [Сервер (Express)]
                                                                           |
                                                    (Установка заголовков text/event-stream)
                                                                           |
                                                      (Постоянное открытое TCP-соединение)
                                                                           |
                                                    [Слушатель событий Node.js EventEmitter]
                                                                           |
                                                    --(2. Отправка порций данных по сети)-->
```

### Цепочка микро-шагов:
1.  **Инициация со стороны клиента**: Сразу после получения ID задачи или при загрузке страницы фронтенд-скрипт создает объект `new EventSource('/api/events?clientId=...')`.
2.  **Запрос на установку соединения**: Браузер отправляет стандартный сетевой запрос `GET` на сервер.
3.  **Принятие запроса сервером**: Маршрутизатор направляет запрос в обработчик эндпоинта `/events`.
4.  **Установка потокового режима**: Сервер отправляет специальные HTTP-заголовки, которые сообщают браузеру, что соединение закрывать нельзя, а данные будут поступать непрерывным потоком:
    *   `Content-Type: text/event-stream` — перевод соединения в режим вещания событий.
    *   `Cache-Control: no-cache` — запрет браузеру и промежуточным прокси кешировать пакеты данных.
    *   `Connection: keep-alive` — требование держать TCP-сокет открытым.
5.  **Первичное состояние**: Сервер мгновенно отправляет первый пакет данных — текущее состояние всей очереди задач в формате JSON.
6.  **Подписка на внутренние события**: Сервер привязывает обработчик к глобальному объекту обмена событиями `taskEmitter` (класс `EventEmitter` в Node.js).
7.  **Сетевое удержание (Heartbeat)**: Чтобы сетевое оборудование (роутеры, провайдеры) не закрывало "молчаливое" соединение по таймауту, сервер запускает таймер, который каждые 30 секунд отправляет в сокет пустую строку двоеточия (комментарий `:heartbeat\n\n`).
8.  **Вещание обновлений**: Когда фоновый процесс парсинга обновляет статус задачи (например, меняется процент выполнения с 10% на 20%), в Node.js срабатывает событие `taskUpdate`.
    *   Обработчик перехватывает объект задачи.
    *   Проверяется соответствие `clientId`: если задача приватная, она отправляется только тому клиенту, который ее создал.
    *   Сервер кодирует задачу в строку вида:  
        `event: taskUpdate\ndata: {"id":"report_...", "status":"processing", "progress": 20}\n\n`
    *   Эта строка записывается напрямую в открытый сетевой сокет с помощью метода `res.write()`.
9.  **Принятие на клиенте**: Браузер ловит это событие по сети, парсит JSON во внутреннем обработчике `EventSource.onmessage` и мгновенно перерисовывает интерфейс (например, сдвигает ползунок загрузки).
10. **Закрытие соединения**: Если пользователь закрывает вкладку браузера, сокет со стороны клиента закрывается. Сервер перехватывает событие `req.on('close')`, очищает таймер пинга (`heartbeat`) и отписывается от событий `taskEmitter`, освобождая оперативную память.

## Взаимодействие 3: Запрос курсов валют
**Тип**: Исходящий HTTP-запрос от сервера к стороннему API обмена валют

```
[Сервер (Express Pipeline)] --(1. HTTP GET с API-ключом)--> [Валютный API (Exchange Rate)]
                                                                     |
                                                          (Конвертация курсов)
                                                                     |
                                   <--(2. Ответ HTTP 200 с JSON)--   
```

### Цепочка микро-шагов:
1.  **Триггер конвейера**: Как только очередь запускает задачу на выполнение, управление передается в `pipeline.js`. Первым делом конвейеру необходимы курсы валют.
2.  **Подготовка сетевого клиента**: Сервер инициализирует HTTP-клиент `axios`. Он считывает ключи доступа к валютному API из настроек среды (файл `.env`).
3.  **Отправка сетевого запроса**: Делается GET-запрос к внешнему серверу валютных котировок.
4.  **Ожидание и лимиты времени (Timeout)**: На запрос устанавливается таймаут в 10 секунд. Если сторонний сервер не ответит за это время, Node.js принудительно разорвет соединение и выбросит ошибку, чтобы конвейер не завис бесконечно.
5.  **Получение ответа**: Сторонний сервер возвращает HTTP-ответ со статусом `200 OK` и телом в формате JSON, содержащим курсы валют по отношению к базовой валюте (например, доллару или рублю).
6.  **Нормализация данных**: Сервер считывает этот JSON, сохраняет курсы в память текущей задачи для последующего пересчета зарплат вакансий в белорусские рубли (BYN).

## Взаимодействие 4: Глубокий парсинг вакансий через API HeadHunter
**Адрес**: `https://api.hh.ru/vacancies`  
**Тип**: Внешнее сетевое взаимодействие по протоколу HTTP/1.1 с авторизацией OAuth2

```
[Сервис HhParser] --(1. HTTP POST с Client ID & Secret)--> [Сервер авторизации HH.ru]
                                                                     |
                                                           (Генерация OAuth2 токена)
                                                                     |
                  <--(2. Ответ HTTP 200 с Access Token)--            |
                                                                     |
[Сервис HhParser] --(3. HTTP GET /vacancies с токеном в Header)------> [API HH.ru]
                                                                     |
                                                             (Поиск вакансий)
                                                                     |
                  <--(4. Ответ HTTP 200 с массивом JSON)--           |
                                                                     |
[Сервис HhParser] --(5. Параллельные GET-запросы по ID вакансий)------> [API HH.ru]
                                                                     |
                                                            (Детальное описание)
                                                                     |
                  <--(6. Ответы HTTP 200 с полными описаниями)--     
```

### Цепочка микро-шагов:
1.  **Проверка авторизации**: Модуль `HhParser` проверяет наличие сохраненного OAuth2-токена в памяти.
    *   Если токена нет или его срок действия подходит к концу, сервер совершает сетевой POST-запрос к `/token` адресу HeadHunter с передачей `Client ID` и `Client Secret` приложения.
    *   HH.ru возвращает токен доступа (`access_token`), который сохраняется в кэше сервера на несколько часов. Если авторизация не удалась, парсер переключается в анонимный режим.
2.  **Формирование запроса списка вакансий**: Парсер генерирует URL-параметры поиска: текстовый запрос, регион поиска (area), количество элементов на страницу (20 штук) и период публикации.
3.  **Сетевой запрос списка (Пагинация)**:
    *   Сервер выбирает случайный юзер-агент (строка, идентифицирующая браузер/клиент) из заготовленного списка для снижения вероятности блокировок.
    *   Отправляется HTTP GET-запрос на `https://api.hh.ru/vacancies` с заголовком `Authorization: Bearer <токен>` (если токен активен).
4.  **Обработка блокировок и лимитов (Rate Limiting & Retry)**:
    *   Если HH.ru возвращает статус `HTTP 403` или `429` (вы исчерпали лимит запросов), парсер запускает алгоритм задержки: соединение закрывается, скрипт засыпает на 2 секунды (при первой ошибке), затем на 4 секунды, а затем на 8 секунд, пытаясь повторить запрос.
    *   Если после 3 попыток сервер все равно заблокирован, генерация отчета завершается с ошибкой.
5.  **Получение списка вакансий**: При успешном ответе (`HTTP 200 OK`) парсер получает JSON-список вакансий (где содержатся только краткие аннотации и ID вакансий) и сохраняет их в массив.
6.  **Глубокий парсинг описаний (Deep Scrape)**: Если включен глубокий анализ, сервер должен получить полное описание каждой вакансии.
    *   Создается пул задач с ограничением конкурентности: одновременно отправляется не более 3 сетевых запросов, чтобы не перегружать сервер HeadHunter и не получить блокировку IP.
    *   Для каждой вакансии из списка отправляется запрос `GET https://api.hh.ru/vacancies/<ID_вакансии>`.
    *   Между группами запросов выдерживается случайная пауза от 1 до 2 секунд (рандомизированный сетевой джиттер).
7.  **Объединение данных**: Полученные по сети полные описания вакансий очищаются от HTML-тегов с помощью регулярных выражений и прикрепляются к объектам вакансий в памяти конвейера.

## Взаимодействие 5: Веб-скрейпинг Хабр Карьеры с адаптивным обходом блокировок
**Адрес**: `https://career.habr.com/vacancies`  
**Тип**: HTTP-запросы с получением HTML-страниц и парсингом дерева элементов (Scraping)

```
[Сервис HabrParser] --(1. HTTP GET с маскировкой под Chrome)--> [career.habr.com]
                                                                        |
                                                             (Генерация HTML-страницы)
                                                                        |
                    <--(2. Ответ HTTP 200 с HTML кодом)--               |
                                                                        |
   (Парсинг DOM с помощью Cheerio на стороне сервера)                   |
                                                                        |
[Сервис HabrParser] --(3. Запросы GET страниц вакансий по очереди)-----> [career.habr.com]
                                                                        |
     (Обнаружение HTTP 429 Too Many Requests / Блокировки ботов)        |
                                                                        |
[Адаптивный Backoff: Снижение потоков до 1, пауза 8 сек между запросами]|
                                                                        |
                    <--(4. Медленное, успешное скачивание HTML)--       
```

### Цепочка микро-шагов:
1.  **Формирование запроса к Хабру**: У Хабр Карьеры нет публичного API. Модуль `HabrParser` собирает GET-параметры: `q` (строка поиска) и `page` (номер страницы).
2.  **Маскировка сетевого запроса**: Чтобы сервера Хабра не распознали в Node.js автоматического бота, формируется расширенный набор HTTP-заголовков (Headers):
    *   Случайный полноценный `User-Agent` (имитирующий реальные браузеры Chrome, Firefox или Safari на Windows/Mac).
    *   Заголовки сетевого окружения: `Accept-Language`, `Connection: keep-alive`, `Upgrade-Insecure-Requests`, а также специальные служебные заголовки `Sec-Ch-Ua`, имитирующие поведение современного браузера.
3.  **Сетевой запрос страницы**: Отправляется HTTP GET-запрос.
4.  **Анализ ответа и Адаптивный Backoff (Защита от банов)**:
    *   Если Хабр блокирует сетевой запрос, возвращая ошибку `HTTP 429` (слишком много запросов) или `HTTP 403 Forbidden`, парсер активирует аварийный режим.
    *   Количество параллельных сетевых потоков снижается до 1 (строго последовательные запросы).
    *   Интервал задержки между следующими запросами принудительно увеличивается до **8 секунд**.
    *   Только после успешного получения ответа система плавно возвращается к стандартному режиму работы (2 параллельных потока, паузы 2-5 секунд).
5.  **Парсинг HTML на сервере**: Полученный сырой HTML-текст передается в библиотеку `cheerio`.
    *   Библиотека строит виртуальное дерево элементов в памяти сервера (DOM).
    *   С помощью CSS-селекторов вытаскиваются узлы с классом карточек вакансий `.vacancy-card`.
    *   Извлекаются текстовые поля: название компании, город, зарплатная вилка, ключевые навыки и ссылка на полную страницу.
6.  **Глубокий сбор данных (Deep Scrape)**:
    *   Для сбора полных текстов вакансий парсер отправляет последовательные GET-запросы по ссылкам собранных вакансий.
    *   Внедряется обязательная пауза в 3 секунды перед каждым сетевым переходом, чтобы защитить IP-адрес сервера от постоянного бана.
    *   Полученные полные HTML-страницы детального описания парсятся, из них вырезается чистый текст требований и обязанностей.

## Взаимодействие 6: Сетевой мост к ИИ через автоматизацию Chromium
**Тип**: Локальное сетевое IPC-взаимодействие (Node.js $\rightarrow$ Python) + Внешнее сетевое взаимодействие (Playwright $\rightarrow$ Веб-интерфейс ИИ)

```
[Служба ИИ Node.js] --(1. child_process.spawn: запуск скрипта)--> [Python Bridge]
                                                                        |
                                                         (Инициализация Playwright)
                                                                        |
                                                         (Запуск Chromium с профилем)
                                                                        |
  [Скрытый Chromium] --(2. Вход по сети на сайт ИИ с куками)----> [DeepSeek / Google AI]
                                                                        |
                                                           (Ввод промпта в textarea)
                                                                        |
                                                          (Эмуляция клика на кнопку)
                                                                        |
  [Скрытый Chromium] <-- (3. Парсинг ответа из HTML DOM) ------- [DeepSeek / Google AI]
                                                                        |
  [Python Bridge]     --(4. Запись JSON в поток stdout)---------> [Node.js Сервер]
```

### Цепочка микро-шагов:
1.  **Разбиение на партии (Батчинг)**: Чтобы не отправлять огромные тексты и экономить лимиты ИИ, служба `ai.js` разбивает собранные вакансии на мелкие пакеты по 5-10 штук.
2.  **Формирование промпта**: Генерируется детальная инструкция для ИИ на русском языке с требованием вернуть строго валидный JSON-объект, содержащий извлеченные навыки, технологии, грейд и требования к опыту работы.
3.  **Запуск локального моста**: Node.js использует системную библиотеку `child_process` и выполняет команду запуска Python-интерпретатора, передавая ему аргументы:
    *   Путь к скрипту моста: `server/services/browser_ai_bridge.py`.
    *   Имя модели: `--model deepseek` или `google_ai_studio`.
    *   Путь к папке профиля браузера: `--profile-dir data/browser_profiles/deepseek`.
    *   Сам текст промпта: `--prompt <текст>`.
    *   Флаги: `--headless` (запуск браузера в скрытом режиме без отображения окон).
4.  **Управление браузером из Python**:
    *   Скрипт на Python запускает библиотеку `majorchik-api` (которая под капотом использует Playwright/Puppeteer для управления браузером Chromium).
    *   Открывается скрытый инстанс браузера Chromium с использованием указанной папки профиля (это важно, так как в профиле сохраняются сессии, куки авторизации и настройки обхода Cloudflare).
5.  **Сетевое обращение к веб-интерфейсу LLM**:
    *   Браузер Chromium загружает страницу веб-интерфейса ИИ (например, официальный чат DeepSeek или панель Google AI Studio).
    *   Скрипт автоматизации находит HTML-элемент текстового поля ввода (`textarea`), эмулирует фокус и посимвольно (или через буфер обмена) вводит сгенерированный промпт.
    *   Эмулируется клик по сетевой кнопке "Отправить запрос".
6.  **Ожидание генерации ответа**:
    *   Браузер ожидает, пока ИИ сгенерирует ответ. Сетевой веб-интерфейс ИИ постепенно выводит текст (Streaming).
    *   Скрипт автоматизации мониторит изменения в DOM-дереве страницы браузера. Как только кнопка "Стоп" сменяется кнопкой "Повторить запрос" (или исчезает индикатор генерации), процесс считывания считается завершенным.
7.  **Извлечение текста и закрытие браузера**:
    *   Скрипт вычитывает текстовое содержимое последнего блока ответа из HTML-кода страницы чата.
    *   Браузер Chromium корректно закрывается, освобождая оперативную память и сетевые порты автоматизации.
8.  **Передача данных обратно в Node.js**:
    *   Python-скрипт упаковывает полученный ответ в JSON-структуру и выводит ее в стандартный системный поток вывода (`sys.stdout.write`).
    *   Node.js-сервер слушает поток вывода дочернего процесса (`pyProcess.stdout.on('data')`), собирает текстовые порции данных в единый буфер.
    *   При закрытии процесса Python с кодом `0` Node.js парсит буфер как JSON.
9.  **Валидация JSON**: Извлеченный текст очищается от лишних Markdown-разметок (таких как ```json ... ```). Из него выделяется чистый JSON-объект с метаданными вакансий, который интегрируется в отчет.

## Взаимодействие 7: Генерация AI-сводки по готовому отчету
**Маршрут**: `POST /api/reports/:id/summary`  
**Тип**: Клиент-Серверный REST-запрос (HTTP/1.1) + Локальный запуск ИИ-моста

```
[Браузер] --(1. HTTP POST с выбранными навыками)--> [Express Маршрутизатор]
                                                            |
                                               (Проверка: занят ли ИИ парсингом?)
                                                  /                         \
                                              (Да)                          (Нет)
                                              /                               \
                    [HTTP 409 Conflict: ИИ занят]                 [Чтение файла отчета из data/]
                                                                              |
                                                                  [Генерация промпта рекрутера]
                                                                              |
                                                                  [Запуск моста к DeepSeek]
                                                                              |
                     <--(2. Ответ HTTP 200 с Markdown текстом)--              |
                                                                  [Сохранение сводки в файл отчета]
```

### Цепочка микро-шагов:
1.  **Действие пользователя**: На странице готового отчета пользователь может выбрать свои ключевые навыки (стек технологий) и нажать кнопку "Составить портрет кандидата".
2.  **Запрос к серверу**: Браузер отправляет HTTP POST-запрос на адрес `/api/reports/<ID_отчета>/summary`. В теле запроса передается JSON-массив выбранных пользователем навыков `selectedSkills`.
3.  **Проверка состояния ресурсов (Mutex / Блокировка)**:
    *   Сервер проверяет статус фоновой очереди задач.
    *   Если в данный момент ИИ занят обогащением новых вакансий в фоновом режиме, сервер возвращает статус `HTTP 409 Conflict` с ошибкой: *"Данная функция пока недоступна, пока идет работа с ИИ (парсинг новых вакансий)"*. Это предотвращает одновременный запуск двух скрытых браузеров, который привел бы к конфликту сессий Chromium и перегрузке процессора.
4.  **Чтение отчета**: Если ресурсы свободны, сервер считывает файл отчета с жесткого диска (`data/reports/<ID_отчета>.json`), парсит его содержимое и собирает общую статистику (топ-15 навыков, самый частый формат работы, средние зарплаты).
5.  **Кэширование ответов**: Сервер сравнивает массив переданных навыков с теми, по которым сводка, возможно, уже генерировалась ранее (`aiSummarySkills` в JSON отчете). Если наборы навыков полностью совпадают, сервер не делает повторных запросов к ИИ, а мгновенно возвращает кэшированную сводку из файла отчета, экономя время и сетевой трафик.
6.  **Генерация промпта IT-рекрутера**: Если кэша нет, сервер формирует развернутый промпт для ИИ, выступающего в роли экспертного рекрутера, включая туда общую статистику отчета и стек пользователя для проведения Job Matching анализа.
7.  **Запуск сетевого моста ИИ**: По аналогии со Взаимодействием 6 запускается Python-скрипт автоматизации браузера, который направляет запрос в DeepSeek или Google AI Studio.
8.  **Обновление отчета**: Полученный текстовый Markdown-анализ от ИИ записывается внутрь объекта отчета в поле `aiSummary`. Измененный объект отчета перезаписывается на жесткий диск.
9.  **Ответ клиенту**: Сервер отправляет клиенту статус `HTTP 200 OK` с телом ответа в формате JSON, содержащим сгенерированный красивый Markdown-текст портрета кандидата. Браузер с помощью библиотеки-рендерера отображает этот текст пользователю в удобном визуальном блоке.
